Toko against shared-tooling, ic-host-* and ic-metrics

An audit of how toko measures up to the new shared engineering baseline and the host crates, where those crates fall short for an app like toko, and a plan for adding ic-metrics.

shared-tooling 0.1.14 (25e7ce8)
ic-host-tooling 0.3.2
ic-metrics 0.2.5
Canic 0.110.48 · IcyDB v0.258.0

Summary

Blocking

project_instance can't be deployed

With the release profile and the nightly size recipe it builds to 11.03 MB. Canic refuses anything over 10 MiB; the IC itself allows 12 MiB.

13 of 21 rules missed

shared-tooling adoption is a project

2 rules met, 6 partly. Most fixes are small. Three need a team decision first: agent commits, the PR-based release flow, and the IC tool versions.

Through Canic

ic-host-* belongs in Canic, not toko

Toko has no host-side Rust to plug these crates into. Canic duplicates them in five places and should adopt them; toko benefits through Canic upgrades.

Design ready

ic-metrics fills real gaps

Canic and IcyDB already record endpoint totals and DB cost. Missing: per-call peaks, write-batch shape (the E263 warning sign), budget stops and timer jobs.

Decisions needed

  1. Canic's 10 MiB limit. File an upstream issue and PR to use the IC's 12 MiB per network? Until a release lands, use a locally patched canic to unblock local deploys?
  2. Agent commits. The baseline says agents never commit (DRAGGINZGAME.md 45–50). Toko currently has agents commit under maintainer review. Adopt the rule, or request an exception?
  3. Release flow. The shared release runner pushes the branch and tag straight to the release branch. Toko releases through a release/vX.Y.Z PR and tags after merge. Request a PR-gated variant upstream, or an exception?
  4. IC tool versions. The shared defaults (PocketIC 16, ic-wasm 0.11.1) would break ledger_test and may break post-processing. Keep a toko-owned version list (the rules allow it) or upgrade toko to the shared versions?
  5. Workspace move. The rules want crates/ and apps/<app>/<role>. Moving fleets/ and backend/src is the largest item, with no runtime benefit. Do it now, or record an interim exception?
  6. ic-metrics scope. Operator dashboard (endpoint, admin proxy and Admin tab) or tuning data only? project_instance only first, or every role?
  7. ~20 endpoints with no consumer in the repo. Owners need to confirm before removal (callers outside the repo weren't searched).

The Wasm size limit

Canic 0.110.47 renamed CURRENT_IC_MAINNET_CODE_SECTION_LIMIT_BYTES to SUPPORTED_CODE_SECTION_LIMIT_BYTES and kept it at 10 MiB. The constant is still 10 MiB in 0.110.52 and applies to every network. The IC's documented limit and the IC source on master are both 12 MiB. project_instance fitted earlier in the week; the contract-system merge (#1755, +16.9k lines) is the likely cause, though the pre-merge build wasn't remeasured.

  • Local test: the 11.03 MB build installed on toko's local replica. The only failure was in init, which ran because the module had been accepted. Mainnet and staging replica versions weren't checked.
  • Optimiser passes (--converge, --low-memory-unused) save about 80 KB, not enough on their own.
  • Where the size goes: Candid encoding 19.7%, icydb_core 13.6%, alloc 11.3%, the instance crate 10.0%, core 8.2%, canic_core 7.3%, design 7.1%.
  • The nightly -Zbuild-std recipe (about 2× compile time) exists only because of Canic's constant. Toko's own size check (wasm_metrics.js) also calls 10 MiB "the IC limit".

Suggested order

  1. Quick, low-risk pins: catalog, git rev, exceptions file, action SHAs, changelog, baseline header.
  2. The shared hook, which also ends the mass re-staging.
  3. Pinned tools with a toko-owned version list.
  4. The release contract, once the PR-flow question is settled.
  5. The workspace move and macOS CI last.

What toko could give back

  • An IC install-limit gate. Nothing in shared-tooling checks Wasm size or function count.
  • The row-at-a-time write lint, which belongs in the IcyDB repo.
  • A frontend / npm lock and Node version rule. shared-tooling has none.
  • A formatting adapter for mixed Rust and frontend repos. The hook rules ask for one but don't provide it.

Bugs in toko's own tooling

  • wasm_metrics.js counts imported functions (the IC counts only defined ones), misparses imported globals, and has no bounds checks.
  • Two post-processing pipelines disagree with each other and with Canic. A stale ic-wasm 0.9.11 wrapper is still first on PATH in bin/build_project_instance.sh.
  • The size recipe defaults off in build_common.sh and on in dev_canic_local.
  • On macOS (no flock), upgrade_canisters.sh silently skips its planner lock.

Gaps in the crates

  • No IC install-limit policy. Every consumer hard-codes its own numbers.
  • WasmFacts lacks imports, globals, exported-name totals, custom-section totals and visibility.
  • AdmittedTool can't admit by version range or without a digest.
  • No chunked digest or "hash of a gzipped module" helper. No Candid compatibility check.
  • API issues: encode_gzip exposes flate2::Compression; ic-host-fs has overlapping readers, one of them unbounded; some typed errors are flattened to io::Error.

ic-metrics plan

ic-metrics 0.2.5 is on crates.io: no_std, no dependencies, with MeasurementSummary and MeasurementHistogram. It is not in toko's dependency graph yet. Neither Canic 0.110.x nor IcyDB v0.258 uses it. IcyDB uses 0.2 from v0.266.0.

Already measured (don't duplicate)

  • Canic: per-endpoint call count and total instructions for every #[canic_update]/#[canic_query], through canic_observability. No peaks; query results are discarded; toko's raw timers aren't covered.
  • IcyDB: per-entity hits, total and max instructions (icydb_metrics), already in the Admin metrics view.
  • Toko's probe.rs: log lines only, on 8 endpoints.

Upstream issue candidates

Drafts only. Nothing has been filed.

Canic

  • Use the IC's 12 MiB code-section limit, configurable per network (artifact_io/wasm/mod.rs:12).
  • Adopt ic-host-* in five duplicated places: Wasm parsing, durable writes, tool installation, ICP response decoding and tool resolution.
  • canic-cli 0.110.48 doesn't compile on macOS (durable_io u32 vs u16).

ic-host-tooling

  • IC install-limit policy module with sourced constants and per-network overrides.
  • More WasmFacts fields; version-range admission; chunked digest helpers; a Candid compatibility check.
  • API fixes: hide flate2, consolidate the readers, keep typed errors.
  • Mark the old ic-host-tools repo as superseded.

shared-tooling

  • A PR-gated release variant.
  • A Wasm limit gate.
  • Frontend/npm rules.
  • Audit methods that treat the Candid service as the public surface and account for Wasm budget.

What was checked

  • Mostly read-only: source, docs, manifests and git history in toko and the four cloned repos, plus Canic 0.110.48 and 0.110.52 and IcyDB v0.258.0 from the cargo cache. Nothing from the audits was built, run or clippy-checked.
  • Measured: project_instance sizes (release + size recipe, extra wasm-opt passes, a per-crate profile) and one install of the 11.03 MB module on toko's local replica.
  • Fetched: the IC's limits from the internetcomputer.org resource-limits page and dfinity/ic master.
  • Not checked:
    • whether mainnet subnets and toko's pinned PocketIC already run the 12 MiB limit;
    • callers outside this repo for the "unused" endpoints;
    • security or authorization correctness;
    • Wasm savings from any proposed refactor.
  • Spot-checked by hand: the billing-seed Admin promotion, the duplicate endpoints, the debug logging, the trusted_rows and update_inventory_statuses copies, and burn_holdings.
